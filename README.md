# Locker proxy (Смысл 1)

Свой софт **рядом** с локером: сервер-прослойка над открытым веб-API терминала
(`192.168.11.242:8088`) + веб-UI сетки 43 ячеек. Терминал остаётся как есть,
в него ничего не пишется — только чтение статуса и (в LIVE) команда открыть ячейку.

## Запуск

Зависимостей нет, только стандартная библиотека Python (проверено на 3.14).

```bash
py server.py                 # DRY_RUN ВКЛ (безопасно, по умолчанию) — открытие не шлётся
DRY_RUN=0 py server.py       # LIVE — команды открытия уходят реально
```

Открыть UI: http://127.0.0.1:8000

## Переменные окружения

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `DRY_RUN` | `1` | `1` = открытие только логируется; `0` = шлётся на терминал |
| `TERMINAL_URL` | `http://192.168.11.242:8088` | адрес терминала |
| `PORT` | `8000` | порт прослойки |
| `HOST` | `0.0.0.0` | интерфейс (0.0.0.0 = виден в LAN) |
| `TERMINAL_TIMEOUT` | `8` | таймаут запроса к терминалу, сек |

## API прослойки

- `GET /api/health` — жив ли терминал, режим DRY_RUN
- `GET /api/cells` — 43 ячейки, статус (биометрия вырезана)
- `POST /api/open/{n}` — открыть ячейку 1–43 (в DRY_RUN только лог)

## Безопасность (важно)

- **DRY_RUN включён по умолчанию.** Открытие уходит на терминал только при `DRY_RUN=0`.
- Прослойка зовёт лишь два upstream-роута: `GET /GetBoxList`, `POST /OpenBox`.
  Опасные (`/AllOpenBox`, `/uploadApk`, `/RestartShutdown`, биометрия, порт 14035)
  намеренно не подключены.
- Биометрические поля (`personidArray`, `card`) вырезаются и наружу не отдаются.
- Терминал (AndServer) случайно рвёт ~30% коннектов — прослойка гасит ретраями (5x + User-Agent).

## Заметки

- `HOST=0.0.0.0` виден всем в LAN. Для приватности запускать с `HOST=127.0.0.1`.
- Занятые ячейки на момент разработки: 11, 12, 17, 18, 25 (state=1), 13 (state=2, особая).
  Для теста открытия брать заведомо ПУСТУЮ (state=0).

# Постаматная платформа (`backend/`)

Второй, основной проект этого репозитория: бэкенд сети постаматов на FastAPI +
SQLAlchemy 2.0 (async) + Alembic. К локер-прослойке выше отношения не имеет —
общий у них только репозиторий.

Docker пока не используется, Postgres и Redis тоже: база — SQLite, одноразовые
коды и счётчики лимитов лежат в процессе (`app/core/kvstore.py`).

## Запуск

```powershell
.\run.ps1                    # http://127.0.0.1:8000
.\run.ps1 -Port 9000
.\run.ps1 -NoMigrate         # без alembic upgrade head
```

Скрипт создаёт `backend\.venv`, если его нет, ставит зависимости, копирует
`.env` из `.env.example`, накатывает миграции и поднимает uvicorn с `--reload`.

**Порт 8000 по умолчанию занимают оба проекта** — и локер-прослойка, и бэкенд.
Одновременно поднимать только с разными портами: `.\run.ps1 -Port 8001` либо
`PORT=8001 py server.py`.

- Swagger UI — http://127.0.0.1:8000/docs
- ReDoc — http://127.0.0.1:8000/redoc
- OpenAPI — http://127.0.0.1:8000/openapi.json

## Проверка API

```powershell
cd backend
.\.venv\Scripts\python.exe -m pytest -q                      # тесты
.\.venv\Scripts\python.exe -m scripts.smoke                  # сквозной прогон API
.\.venv\Scripts\python.exe scripts\contract_coverage.py      # какие ручки контракта отвечают
.\.venv\Scripts\python.exe scripts\contract_coverage.py --all # то же, вместе с админкой и киоском
.\.venv\Scripts\python.exe scripts\contract_walk.py          # совпадают ли тела ответов со схемой
.\.venv\Scripts\python.exe scripts\serve_seeded.py           # сервер на :8100 с данными и готовыми токенами
```

Поверх `serve_seeded.py` гоняется schemathesis — property-based проверка по
контракту; так нашлись два 500-х на необработанном вводе и порядок проверок,
при котором неаутентифицированный запрос узнавал про недостающий заголовок
раньше, чем его разворачивали:

```powershell
.\.venv\Scripts\python.exe -m schemathesis.cli run ..\postbox-contract\openapi.yaml `
  --url http://127.0.0.1:8100/api/v1 --include-path-regex admin `
  -H "Authorization: Bearer <admin_token из первой строки serve_seeded>"
```

`scripts/smoke.py` дёргает приложение в том же процессе через ASGI-транспорт, а
не по сети: одноразовые коды живут в памяти процесса, и внешний клиент не смог
бы прочитать код, чтобы довести логин до конца. База — отдельный временный файл,
`dev.db` не трогается. Ручки ещё не написанных задач помечаются `SKIP`.

## Структура

| Каталог | Что внутри |
|---|---|
| `backend/app/core/` | инфраструктура: настройки, БД, ошибки, идемпотентность, пагинация, лимиты, безопасность |
| `backend/app/modules/` | предметные области: `identity`, `catalog`, `booking`, `payments`, `custody`, `notify`, `audit` |
| `backend/app/api/` | роутеры по аудитории: `public`, `mobile`, `admin` |
| `backend/app/workers/` | фоновые задачи |
| `backend/alembic/` | миграции |
| `backend/tests/` | тесты, разложенные по модулям |

Модули не импортируют модели друг друга — только вызывают сервисные функции.
`app.core` не импортирует из `app.modules`.

## Что умеет бэкенд

- Клиент: вход по одноразовому коду, список городов и типов ячеек, список
  постаматов с часами работы, `GET /api/v1/postamats/{id}/availability` —
  сколько ячеек каждого размера свободно и по какой цене.
- Бронирование: клиент выбирает **размер**, а не ячейку; ячейка выдаётся
  атомарно и держится 10 минут (`HOLD_MINUTES`), продлить бронь можно дважды
  (`POST /bookings/{id}/extend-hold`). Кодов два, а не три: код закладки
  выдаётся сразу, код получения — только когда посылка уже в ячейке. Курьер
  получает код закладки и ничего больше, поэтому забрать посылку он не может.
  Плайнтекст возвращается ровно один раз — в ответе, который код выпускает; в
  базе только хеши, поэтому «отправить тот же код повторно» физически
  невозможно, и ротация выпускает новый, убивая старый.
- Есть список броней (`?scope=active|history`, курсорная пагинация), карточка
  брони, таймлайн `GET /bookings/{id}/timeline`, отмена, ротация обоих кодов и
  передача права получения на другой номер.
- `POST /api/v1/bookings` **требует заголовок `Idempotency-Key`** и без него
  отвечает 400 `IDEMPOTENCY_KEY_MISSING`. Повтор с тем же ключом возвращает ту
  же бронь, а не занимает вторую ячейку: двойное нажатие кнопки или ретрай после
  обрыва иначе стоят реальной ячейки на десять минут. Тот же ключ с изменённым
  телом — 409 `IDEMPOTENCY_KEY_REUSED`. Владелец ключа определяется по токену,
  так что два клиента за одним NAT не видят ответы друг друга.
- Оплата: `POST /bookings/{id}/payments` `{bank_code, return_url}` возвращает ссылку провайдера, результат
  приходит подписанным вебхуком `POST /webhooks/payments/{provider}`. Данные карты
  на наш сервер не попадают — иначе проект уезжает в PCI DSS SAQ-D. Пока работает
  мок-провайдер: банк не назван, интерфейс `PaymentProvider` под него готов.
- Просрочка: `awaiting_pickup → expired → grace → overdue`, воркером по часам.
  Плата за просрочку не берётся ни на одной стадии, забрать посылку можно до
  самого изъятия. Льготный период не сгорает, пока постамат закрыт.
- Изъятие: `POST /admin/custody` — акт с описанием, который и освобождает ячейку;
  дальше выдача на стойке или утилизация. Фото в акте нет (см. ниже).
- Уведомления: лента в приложении (`GET /me/notifications`), настройки
  (`GET/PATCH /me/notification-settings`), push-токены устройств, SMS через
  `SmsProvider`. Одноразовый код входа и курьерский PIN уходят этим же каналом.
- Оператор: учётные записи и роли, клиенты, постаматы (включая фото), типы
  ячеек, ячейки (в том числе создание шкафа целиком через `POST /admin/cells/bulk`),
  тарифная матрица, брони, очередь изъятия, устройства, статистика
  (`/admin/stats/*`, включая рабочую очередь `GET /admin/stats/attention`),
  журнал событий с выгрузкой в CSV и живая лента `GET /admin/realtime/stream`
  (Server-Sent Events поверх журнала, без брокера).
- Каждая админская ручка проверяет право (`postamats.write`, `custody.read`,
  `cells.remote_open` и так далее), а каждое изменение состояния пишет в журнал,
  называя оператора. Открытие двери из офиса — отдельное право, не часть
  `cells.write`.

Киоск и открытие дверей — план 3. `POST /admin/cells/{id}/remote-open` уже
существует, проверяет право и пишет в журнал, но честно отвечает 503
`DEVICE_OFFLINE`: агента замка, которым он командовал бы, ещё нет.

## Контракт фронта

`postbox-contract/openapi.yaml` — источник истины для трёх фронтов: два веба
генерируют клиент через `orval`, Flutter — через `openapi-generator`. Поэтому
несовпадение имени поля там не косметика, а ошибка компиляции в трёх кодовых
базах. Клиентский контур сервера приведён к этому файлу целиком: 30 из 30
операций отвечают, тела ответов проверяются `scripts/contract_walk.py`.
Расхождения, которые остались, и то, чего ещё нет, перечислены в
`postbox-contract/HANDOVER-CLIENT.md` — эту записку и получает фронтендер.

Админский контур приведён к тому же файлу: отвечают 86 из 104 операций
контракта. Из оставшихся 17 — киоск (план 3, ждёт железа), одна — возврат
денег, которого в системе нет сознательно. `contract_coverage.py --all`
разделяет эти три случая и завершается с ненулевым кодом, если появится дыра,
про которую никто не принимал решения. Записка для панели —
`postbox-contract/HANDOVER-ADMIN.md`: база, вход, право на каждую ручку, что
является расширением, а не контрактом, и три сознательных расхождения.

`contract_walk.py` проходит обе половины — клиентскую и админскую — и сверяет
каждое тело ответа со схемой: 51 совпадение, ноль расхождений. Сознательные
отклонения объявлены в самом скрипте и печатаются на каждом прогоне, чтобы
отклонение не превратилось молча в норму.

## Возвраты и деньги

Возвратов в системе **нет** — решение принято сознательно. Два следствия видны
явно, а не молча: оплаченная и отменённая до вложения бронь оставляет деньги у
оператора, и успешный вебхук по брони, которую воркер уже снял по таймауту, — это
деньги без услуги. Оба случая пишутся в журнал событий как
`payment.needs_attention` с уровнем `warning` и попадают в рабочую очередь
оператора. Разбираются вручную.

## SMS

`SMS_PROVIDER=log` (по умолчанию) — сообщение только записывается, никуда не
уходит; так работают разработка и тесты. `SMS_PROVIDER=post_tm` шлёт по-настоящему
через `https://sms.post.tm/api/clients/sms/create`, токен в `SMS_API_TOKEN`
(файл `backend/.env`, он в `.gitignore`). Шлюз принимает номер **числом без плюса**:
`+99362615986` уходит как `99362615986`.

## Фото

Фотографируется сам постамат — чтобы клиент узнал машину в холле, а оператор понял,
на какую смотрит. Загрузка: `POST /admin/postamats/{id}/photos` (multipart, PNG/JPEG/WebP,
до 5 МБ), отдача: `GET /api/v1/media/{key}`. Файлы лежат на диске в `backend/media/`
за интерфейсом `FileStorage` — переезд на S3 меняет одну реализацию. В акте изъятия
фото нет.

## Фоновые задачи

```powershell
cd backend
.\.venv\Scripts\python.exe -m app.workers.holds     # снять неоплаченные брони
.\.venv\Scripts\python.exe -m app.workers.overdue   # напоминания и стадии просрочки
```

Запускаются вручную, планировщика пока нет. Без первого первая неоплаченная бронь
держит ячейку вечно; без второго посылка никогда не станет просроченной и никто не
узнает, что ячейку пора освободить.

## Про SQLite и параллельные брони

Аллокация ячейки идёт в транзакции, открытой как `BEGIN IMMEDIATE`: SQLite
допускает одного писателя, и второй запрос ждёт, а не видит ту же ячейку
свободной. Снизу это подстраховано частичным уникальным индексом
`uq_active_booking_per_cell` — одна активная бронь на ячейку на уровне базы.
Postgres понадобится, когда брони начнут упираться в очередь: там то же место
переписывается на `SELECT ... FOR UPDATE SKIP LOCKED`, а вызывающий код не
меняется. Пока один воркер uvicorn — счётчики лимитов и одноразовые коды живут
в процессе.
