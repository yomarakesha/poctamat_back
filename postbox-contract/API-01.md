## 1. Сквозные соглашения

| Тема | Правило |
|---|---|
| База | `/api/v1`. Ломающие изменения — только `/api/v2`, никогда правкой v1 |
| Поля JSON | `snake_case` везде, без исключений |
| Идентификаторы | UUID, предпочтительно v7 (сортируемые по времени) |
| Время | UTC, ISO-8601 с `Z`. Клиенты отображают в `Asia/Ashgabat` |
| Деньги | `{"amount_minor": 1200, "currency": "TMT"}` — целое в минорных единицах. **Float запрещён** |
| Телефон | E.164, `^\+993[0-9]{8}$` |
| Язык | заголовок `Accept-Language`: `tk` / `ru` / `en`. Влияет на человекочитаемые названия, **не на коды ошибок** |
| Пагинация | курсор для лент и журналов, страницы для справочников |
| Сортировка | `?sort=-created_at` — минус означает убывание |
| Множественные фильтры | через запятую: `?status=free,booked` |
| Идемпотентность | заголовок `Idempotency-Key` на всех POST, меняющих состояние |

### Две вещи, которые ломаются чаще всего

**401 против 403.** `401` = токен истёк или отсутствует → клиент обновляет токен и повторяет
запрос. `403` = прав нет → обновление токена не поможет, повторять бессмысленно. Если сервер
путает эти коды, клиент уходит в цикл обновления токена и выглядит как зависший.

**Курсор против страниц.** Журнал и ленты растут во время чтения: страница 2 через минуту
после страницы 1 — это другие записи. Поэтому там курсор. Справочники (города, типы ячеек)
статичны, там страницы — и админке нужен `total` для футера «Показано 1-3 из 124».

## 2. Аутентификация

Четыре независимых субъекта, четыре схемы токенов.

### 2.1 Клиент (мобильное приложение)

```
POST /auth/otp/request   { phone }
      → { request_id, code_length: 6, expires_at, resend_after }
POST /auth/otp/verify    { request_id, code }
      → { access_token, refresh_token, expires_in: 900, profile_complete }
POST /auth/refresh       { refresh_token }
      → новая пара
```

* Access-токен живёт **15 минут**, refresh —長 срок, **одноразовый**. Повторное использование
  refresh-токена аннулирует всё семейство: это признак кражи.
* `code_length: 6` — это **OTP входа**. Не путать с 5-значным PIN ячейки. Это два разных
  секрета с разной длиной, и в UI они выглядят похоже — отсюда путаница в макетах.
* Счётчик попыток OTP живёт на сервере. Клиент читает `details.attempts_left` из тела ошибки
  и рисует остаток. **Никогда не считает сам.**
* `profile_complete: false` → приложение ведёт на экран профиля до всего остального.

### 2.2 Админ

`POST /admin/auth/login` → пара токенов + объект `user` с ролью и **списком разрешений**.
Панель прячет действия, которых нет в списке. Сервер всё равно проверяет права на каждом
вызове: список — подсказка для UI, а не защита.

### 2.3 Устройство (киоск)

`POST /kiosk/auth/provision` один раз при установке: одноразовый код из админки + `hardware_id`
→ долгоживущий `device_token`. Дальше терминал работает по нему и **никогда не показывает
форму логина публике**.

### 2.4 Сотрудник на киоске

`POST /kiosk/auth/staff/login` поверх сессии устройства → короткоживущий `staff_token`.
Это и есть тот экран, который в макетах назван «Сплеш» (`363:3621`). Умирает по таймауту
бездействия вместе с сессией киоска.

## 3. Формат ошибки

Один конверт на все не-2xx ответы:

```json
{
  "error": {
    "code": "CELL_ALREADY_TAKEN",
    "message": "This cell was taken by another booking.",
    "details": { "cell_id": "0190f2c1-6b7a-7c3e-9a11-2f0c9a5d4e70" },
    "trace_id": "0190f2c1-6b7a-7c3e-9a11-2f0c9a5d4eaa"
  }
}
```

* `code` — машинная константа, стабильная навсегда. **Добавить код — не ломающее изменение,
  переименовать — ломающее.**
* `message` — английский, для разработчика и логов. **Пользователю не показывается никогда.**
  Перевод живёт в `packages/i18n` и в ARB-файлах, ключом служит `code`.
* `details` — структурированные подробности: `attempts_left`, `fields`, `alternatives`.
* `trace_id` — то, что называют в тикете.

## 5. Идемпотентность

`Idempotency-Key` — **обязательный** заголовок на каждом POST, меняющем состояние
(в спецификации такие параметры помечены `required: true`).

Правила для бэкенда:

1. Ключ генерирует клиент, это UUID. Область действия — эндпоинт + субъект.
2. Повтор с **тем же ключом и тем же телом** возвращает исходный ответ, включая исходный код
   состояния. Повторного действия не происходит.
3. Повтор с тем же ключом и **другим** телом → `409 IDEMPOTENCY_KEY_REUSED`.
4. Срок хранения ключа — не меньше 24 часов.
5. Ответы 5xx **не** запоминаются: их можно и нужно повторять.

Почему это не украшение: связь в отделениях рвётся посреди запроса. Без ключа повтор
`POST /bookings` бронирует и оплачивает вторую ячейку, а повтор `resend` шлёт человеку
второе SMS с кодом. Оба случая — реальные деньги и реальный звонок в поддержку.

## 6. Пагинация

**Курсор** — журнал, ленты, ячейки монитора, брони, отправления:

```
GET /admin/audit-log?limit=50&cursor=eyJvZmZzZXQiOjUwfQ
→ { "items": [...], "pagination": { "next_cursor": "...", "has_more": true } }
```

**Страницы** — города, постаматы, типы ячеек, клиенты, пользователи:

```
GET /admin/postamats?page=1&per_page=20
→ { "items": [...], "pagination": { "page": 1, "per_page": 20, "total": 124, "total_pages": 7 } }
```

`total` нужен именно на страничных эндпоинтах — футер «Показано 1-3 из 124» нарисован в макетах.

## 7. События реального времени

Админка стартует на **опросе раз в 5 секунд**; источник данных на клиенте спрятан за
интерфейсом, чтобы заменить его на поток без переписывания экранов.

Поток: `GET /admin/realtime/stream`, `text/event-stream`.

| Тип события | Полезная нагрузка |
|---|---|
| `cell.status_changed` | `cell_id`, `postamat_id`, `from`, `to`, `reason` |
| `cell.door_opened` / `cell.door_closed` | `cell_id`, `occurred_at` |
| `booking.created` | краткая бронь |
| `booking.status_changed` | `booking_id`, `from`, `to` |
| `device.presence_changed` | `device_id`, `status` |
| `device.alert` | `device_id`, `alert_type` (tamper, ups, jam, cert_expiring) |
| `audit.entry_created` | запись журнала целиком |

Переподключение — с `?last_event_id=`. **Клиенты обязаны молча игнорировать неизвестные типы:**
новые события будут добавляться без смены версии API.

## 8. Киоск ↔ локальный агент замков (WebSocket)

Железа нет — это контракт для мока. Мок на TypeScript реализует ровно этот интерфейс, и киоск
тестируется целиком: открытие, датчик двери, заклинивание, потеря связи.

**Адрес:** `ws://127.0.0.1:8765`. Только loopback. Наружу не слушает никогда.
**Формат:** JSON-сообщения, схемы `LockAgentCommand` и `LockAgentEvent` в `openapi.yaml`
(они там ради генерации типов, HTTP-эндпоинтов у них нет).

### Команды (киоск → агент)

| `command` | Параметры | Смысл |
|---|---|---|
| `open` | `cell_id`, `hardware_address`, `timeout_ms` | Открыть замок |
| `status` | `cell_id` | Состояние двери и замка |
| `diagnostics` | — | Обойти все замки и датчики |
| `ping` | — | Проверка живости |

### События (агент → киоск)

| `type` | Смысл |
|---|---|
| `agent_ready` | Агент поднялся, плата отвечает |
| `ack` | Команда принята, `command_id` |
| `opened` | Замок сработал |
| `open_failed` | Не сработал, см. `error_code` |
| `door_opened` | Датчик: дверь открылась |
| `door_closed` | Датчик: дверь закрыта — **ключевое событие** |
| `door_timeout` | Дверь не закрыли за отведённое время |
| `sensor_fault` | Датчик не читается |
| `jammed` | Заклинило |
| `tamper` | Вскрытие корпуса |
| `power_state` | Переход на UPS и обратно |
| `pong` | Ответ на `ping` |

`error_code`: `LOCK_NOT_RESPONDING`, `LOCK_JAMMED`, `SENSOR_FAULT`, `BOARD_UNREACHABLE`,
`INVALID_ADDRESS`.

### Нормальный сценарий получения

```
киоск → ядро   POST /kiosk/sessions            { pin, role: owner }
ядро  → киоск  201 { session_id, cell{ id, number, hardware_address }, grant_kind: pickup }
киоск → ядро   POST /kiosk/sessions/{id}/open
ядро  → киоск  200 { status: opening }
киоск → агент  { command: "open", cell_id, hardware_address }
агент → киоск  { type: "ack" }
агент → киоск  { type: "opened" }
   экран «ЯЧЕЙКА ОТКРЫТА · Ожидание закрытия датчика...»
агент → киоск  { type: "door_opened" }
агент → киоск  { type: "door_closed" }
киоск → ядро   POST /kiosk/sessions/{id}/door-closed { closed: true, observed_at }
ядро           ячейка → free, бронь → completed
```

### Что происходит при закладке

Та же цепочка с `role: courier`, но `door_closed` вызывает другое: ячейка становится
`occupied` и **только в этот момент** получателю уходит SMS с кодом выдачи.

### Отказы

* Агент не отвечает на `ping` → баннер потери связи, новые открытия запрещены,
  `LOCK_AGENT_UNAVAILABLE` в ядро.
* **Ядро недоступно, но агент жив** → работает офлайн-режим, см. ниже.
* `door_timeout` → напоминание на экране, `POST /door-closed { closed: false }`, тикет.
  Ячейка остаётся как была.
* `jammed` / `sensor_fault` → ячейка в `maintenance`, событие в журнал, уведомление админу.
### Офлайн-режим

Решение изменилось по итогам сведения с бэкендом. Раньше правило было «нет связи с ядром —
нет открытий»; теперь действует ограниченный офлайн:

| Что | Правило |
|---|---|
| Что кэширует агент | Активные брони своего постамата и **хеши** кодов. Плейнтекста нет нигде |
| Что можно офлайн | **Только выдачу** — посылка уже внутри, код уже выпущен и отправлен |
| Что нельзя офлайн | Закладку, служебное открытие, любое действие сотрудника |
| Срок годности кэша | `offline_ttl` — синхронизировался позже, чем N минут назад → агент отказывает |
| После восстановления связи | Буфер событий уезжает в ядро, журнал догоняет реальность |

Почему именно так. Полный офлайн даёт максимум доступности, но отзыв кода не доезжает:
человек передал получение другому, старый код погашен на сервере, а отвалившийся шкаф всё ещё
его принимает. TTL превращает эту дыру из бессрочной в короткую и измеримую.

Обратная сторона тоже названа честно: пока агент офлайн, «передать получение» не действует
на этом постамате до истечения TTL. Это компромисс, а не бесплатное улучшение.

Закладка офлайн запрещена по другой причине: она порождает новое состояние (ячейка занята,
код выдачи надо выпустить и отправить SMS), а отправить SMS без ядра всё равно нельзя.
Получатель остался бы с посылкой в шкафу и без кода.

## 10. Инварианты, которые нельзя нарушить реализацией

Это не пожелания к стилю. Каждый пункт — либо безопасность, либо деньги.

1. **Pickup PIN не возвращается ни одним эндпоинтом.** Ни отправителю, ни админу, ни в журнале,
   ни в `details` ошибки. Единственный путь наружу — SMS получателю. В ответах есть только
   `pickup_code_sent_at`.
2. **Коды хранятся ключевым HMAC или медленным KDF, не «просто хешем».** У 5-значного кода
   всего 100 000 вариантов — обычный хеш перебирается по украденной базе мгновенно. Ключ
   держится вне БД.
3. **Лимит попыток PIN двойной: на бронь и на постамат.** Три попытки на сессию обходятся
   новой сессией; без лимита на устройство шкаф перебирается за вечер (100 000 комбинаций,
   ~20 живых кодов → попадание примерно 1 к 5 000).
4. **Плейнтекст кода закладки живёт только в ответе, который его выпустил.** Повторно
   прочитать нельзя — можно только выпустить новый через `rotate`, погасив старый.
5. **Освобождает ячейку акт изъятия, а не кнопка.** `POST /admin/custody` с фотографией и
   описанием — единственный путь из `overdue` в свободную ячейку.
6. **Код выдачи уходит только после `door_closed` от датчика.** Не по кнопке, не по таймеру,
   не по факту успешного `open`. Иначе код уедет получателю при пустой ячейке.
7. **Три неверных PIN → ячейка `blocked`.** Снимает только админ, и только ответив, что стало
   с посылкой (`parcel_fate`). Всё это в журнал.
8. **Ячейка закрепляется в момент создания брони, до оплаты.** Клиент не должен заплатить и
   узнать, что ячеек нет. Отсюда удержание на 10 минут (настройка, не константа).
9. **Занятость ячейки вычисляется, а не хранится.** В базе живут только человеческие решения —
   `is_blocked` и `is_maintenance`. Два источника правды об занятости — самая вероятная причина
   ячейки, которая не открывается, или ячейки, проданной дважды. Приоритет для read-model:
   `blocked` > `maintenance` > `occupied` > `booked` > `free`.
10. **Данные карты не проходят через это API.** Ни одного поля PAN/CVC/expiry ни в одной схеме.
    Приложение получает `redirect_url` и открывает страницу банка.
11. **`DELETE` не существует** — кроме удаления фотографии. Постаматы, ячейки, типы, клиенты
    только блокируются: журнал и статистика за прошлые периоды должны оставаться целыми.
12. **Номер ячейки, позиция в сетке и аппаратный адрес — три разных поля.** Совпадение значений
    в пилоте — совпадение, а не правило.
13. **Экспорт журнала потоковый.** Ответ отдаётся чанками, браузер ничего не собирает в памяти.
14. **Офлайн только на выдачу и только в пределах TTL.** Закладку и служебные открытия без
    ядра терминал не выполняет никогда.
15. **Возврат денег — только у оператора.** В мобильном API его нет ни в каком виде;
    предупреждение «возврата не будет» обязано стоять на экране сводки до кнопки оплаты.
16. **Цена фиксируется в момент создания брони.** Правка матрицы тарифов не меняет уже
    созданные брони — иначе человек увидит одну сумму на сводке и другую в чеке.
17. **Срок брони считается по часам работы постамата.** Оплата 12 ч в 19:00 на точке, которая
    закрывается в 20:00, не может истекать в 07:00.

| **Код выдачи** | Не возвращался нигде | Возвращается **один раз**, в ответе на выпуск, владельцу брони. Экран «Курьер» в Figma рисует именно это, и без этого «отправить заново» бесполезно: получатель нигде не зарегистрирован |
| **Три неверных PIN** | Блокировали ячейку | Блокируют **терминал**. Неверный код не сопоставляется ни с одной ячейкой — пока код не совпал, неизвестно, к какой двери человек шёл. Экран киоска говорил неправду |
| **Уникальность кодов** | Не оговорена | Активные коды уникальны **в пределах постамата**. 100 000 комбинаций против ~86 живых кодов в полном шкафу — коллизия примерно в 4% случаев, и тогда проверка не знает, какую из двух дверей открыть |
| **Офлайн после TTL** | Не открывалось ничего | Добавлен break-glass: терминал показывает challenge, оператор по телефону считает response, открывается ровно одна названная ячейка. Без этого посылки запирались до приезда с отвёрткой |
| **Состояние двери** | Слал киоск | Шлёт **агент**. Событие, которое выпускает SMS с кодом, нельзя проводить через вкладку браузера: перезагрузка в неудачную секунду оставляет посылку внутри, а получателя без кода |
| `to_remove` | Не было в enum | Есть. Очередь оператора должна отличать «просрочено» от «сказано идти и вынимать» |
| Дверь не закрылась | Не описано | Бронь остаётся в `awaiting_deposit`, SMS не уходит, поднимается тревога |
| `offline_ttl` | Не назначен | **24 часа** от последней синхронизации, настраивается по постамату |

Про TTL стоит привести его рассуждение целиком, потому что оно нетривиально: цена длинного
TTL — что посылку заберёт тот, кого отправитель **и так назначил**; цена короткого — что живые
люди с живыми посылками упрутся в отказывающий шкаф при обычном обрыве связи, а в отделении
это происходит регулярно. Цены несимметричны, поэтому число ставится на длинную сторону.

### Осталось открытым

1. **Какой эквайер первый.** Все три банка в enum, интеграция будет одна. Банк отдаёт свой API
   и оплата происходит на его странице — то есть на клиентскую часть выбор не влияет вообще.
   Для бэкенда это блокер: без документации не сделать проверку подписи в
   `POST /webhooks/payments/{provider}`.
2. **SMS-провайдер.** Не выбран. Влияет на нас косвенно, но сильно: pickup PIN идёт
   исключительно SMS, и без отчётов о доставке мы не отличим «не пришло» от «не прочитал».
   У бэкенда для этого заложен `POST /webhooks/sms/{provider}`.
3. **Срок хранения после истечения аренды.** Решает Türkmenpoçta. До ответа — серверная
   настройка с дефолтом 24 часа.
4. **Значение `offline_ttl`.** Сколько минут агенту разрешено работать без синхронизации.
   Чем больше, тем дольше живёт отозванный код на отвалившемся шкафу.
5. **Ретеншн холодного архива журнала.** Год в горячей базе решён, архив лежит на сервере,
   но срок хранения архива не назван.

## 13. Что изменилось при сведении с бэкендом

Документ бэкенд-разработчика «Postamat backend — design» от 14.08.2026 разошёлся с черновиком 1
в девяти местах. Все разногласия закрыты; ниже — куда качнулось и почему.

### Принято из его документа

| Что | Почему его вариант лучше |
|---|---|
| **`Booking` вместо `Reservation` + `Shipment`** | Макеты его подтверждают: экран «Курьер» — шаг внутри бронирования, а не отдельная сущность. Курьер стал флагом `deposited_by` + `courier_phone`. Минус таблица, минус четыре эндпоинта |
| **Структурированное расписание постамата** | У меня было `working_hours: "08:00–20:00"` строкой. Это ошибка: от часов работы зависит срок брони. Оплата 12 ч в 19:00 на точке, закрывающейся в 20:00, истекала бы в 07:00 — раньше, чем человек физически может прийти |
| **Лестница просрочки** `expired → grace → overdue → removed → closed` | Было два статуса вместо шести. Интервалы — конфигурация, штрафов нет ни на одной ступени |
| **`CustodyRecord`** | Было `{destination, note}`. Стало: акт с фото и описанием, цепочка передач, судьба через 30 дней. Разница между «ячейка освободилась» и «на спор есть чем ответить» |
| **Занятость вычисляется, а не хранится** | Два источника правды об занятости — самая вероятная причина двойной продажи ячейки |
| **Лимит попыток PIN на постамат** | Его расчёт верен: 100 000 комбинаций, ~20 живых кодов, попадание 1 к 5 000, три попытки на сессию обходятся новой сессией. При 5-значном коде это обязательное требование, а не опция |
| **Хранение только хеша кода** | Отсюда `rotate` вместо `resend` — см. ниже |

### Отклонено или изменено

| Его вариант | Решение | Почему |
|---|---|---|
| Полный офлайн у агента | **Офлайн с TTL и только на выдачу** | Полный офлайн не доставляет отзыв кода: «передать получение» не сработает на отвалившемся шкафу неограниченно долго |
| «PIN показывается один раз» | **`rotate`: повторный запрос выпускает новый код** | Макеты показывают код на экране брони постоянно. Хеш не разворачивается, поэтому «показать снова» невозможно — зато выпустить новый можно, и это безопаснее: код, ушедший не тому человеку, умирает |
| `DELETE` постаматов, городов, тарифов, пользователей | **Только блокировка** | Журнал и статистика за прошлые периоды должны оставаться читаемыми |
| Статус постамата `active / maintenance / offline` | **Статус — решение админа, присутствие — поле устройства** | Постамат может быть заблокирован и офлайн одновременно. Смешивать намерение оператора с состоянием железа нельзя |
| Три назначения кода `deposit / pickup / courier` | **Два гранта на бронь** | Третий код — третья строка в пространстве перебора. Кто закладывает, различается флагом `deposited_by`, а не отдельным кодом |
| Возвраты без ограничений | **Возврат только у оператора** | Клиент возврат запросить не может, но шкаф ломается и деньги списываются дважды независимо от политики |
| Удержание 15 минут | **10 минут, настройка** | Совпадает с таймером на экране сводки в макетах |
| 2FA для админа | **Принято, но нужен экран** | В макетах экрана нет; добавлен в список к дорисовке |

### Чего в его документе не было, и это правится на моей стороне

Всё это бьёт по трём клиентам напрямую, поэтому оно есть в `openapi.yaml` и обязано появиться
в реализации: **единый конверт ошибки и 102 машинных кода** (иначе клиент не отличит «неверный
PIN, осталось 2 попытки» от «ячейка заблокирована» иначе как парсингом текста);
**`Idempotency-Key` на всех изменяющих POST**, а не только на платежах — связь в отделениях
рвётся, и повтор `POST /bookings` без ключа бронирует и оплачивает вторую ячейку;
**деньги целым числом в минорных единицах**; **курсорная и страничная пагинация**;
**UTC ISO-8601 и E.164**; **канал реального времени для монитора админки** — у него WebSocket
предусмотрен только для устройств.

## 12. Как это проверить без бэкенда

```bash
npx @stoplight/prism-cli@5 mock -p 4010 contracts/openapi.yaml
# или в docker-compose:
# docker run --rm -p 4010:4010 -v "$PWD/contracts:/c" stoplight/prism:5 mock -h 0.0.0.0 /c/openapi.yaml
```

**Важно:** Prism монтирует пути **без префикса `/api/v1`** — он берёт их из `paths`, а базовый
путь из `servers` отбрасывает. То есть в dev-сборках `baseUrl` должен быть
`http://localhost:4010`, а не `http://localhost:4010/api/v1`. На проде префикс на месте.

Проверено на этом файле:

```
$ curl -H 'Authorization: Bearer x' localhost:4010/cities
{"items":[{"id":"…","name":"Aşgabat","is_available":true,"postamat_count":6}, …],
 "pagination":{"page":1,"per_page":50,"total":7,"total_pages":1}}

$ curl -X POST localhost:4010/kiosk/sessions -d '{"pin":"88422","role":"owner"}'
{"error":{"code":"PIN_INVALID","message":"Wrong code.",
          "details":{"attempts_left":1,"attempt":2,"max_attempts":3},"trace_id":"…"}}
```

Без заголовка `Authorization` Prism сам отдаёт ветку ошибки — это удобно: сценарий «токен
протух» проверяется без единой строчки кода.

Спецификация проходит `npx @redocly/cli lint` без ошибок. Три оставшихся предупреждения
осознанные: `http://localhost` среди серверов и две схемы `LockAgent*`, которые существуют
только ради генерации типов для WebSocket и не привязаны к HTTP-эндпоинтам.
